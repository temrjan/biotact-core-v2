Что происходит, когда клиент задаёт вопрос

Пишу как есть — чтобы видеть, где можно улучшить качество. Где ожидание расходится с кодом — отмечено жёлтым блоком.

  1. Вопрос приходит. Клиент пишет в Telegram, бот шлёт нам POST /ask с user_id, текстом, именем. Проверяем API-ключ — пускаем дальше.
  2. Подгружаем историю. Из Redis достаём предыдущие сообщения этого клиента (до 10 пар, живут 24 часа). Дописываем туда новый вопрос.
  3. Находим карточку клиента в CRM. Postgres → телеграм-ID. Если клиент новый — создаём; если знакомый — берём его профиль (проблемы со здоровьем, семья, прошлые покупки). Этот профиль потом подмешаем в инструкцию для LLM.
  4. Обогащаем вопрос (для поиска, не для LLM).
    Цель: короткий вопрос "а цена?" сам по себе не найдёт нужную карточку — надо добавить контекст того, о чём шла речь.
    ЛЛМ не переписывает вопрос. Делается это так:
    а) лезем в Postgres за conversation_insights — это то, что с прошлого хода async-агент успел извлечь (упомянутые продукты, симптомы). Если запрос короткий и в инсайте есть продукты → клеим "BIFOLAK NEO IMMUNOCOMPLEX а цена?".
    б) если инсайтов нет — regex проходит по последним 6 сообщениям, ищет ТОЧНЫЕ имена продуктов из жёсткого списка. Нашёл — клеит, нет — клеит просто текст последних 2 сообщений клиента.
    в) если в вопросе есть "цена/стоит/narx/qancha" — в конец дописывается статичная строка "цены на продукты BIOTACT прайс-лист...".
  5. Превращаем обогащённый текст в вектор (embedding). OpenAI text-embedding-3-large → 3072 числа. Один вызов, одна попытка.
  6. Ищем похожие чанки в Qdrant. База — одна коллекция knowledge-evolution на всю компанию, фильтр department_id = askbiotact. Возвращаем до 10 чанков с похожестью ≥ 0.30 (косинус). Это карточки продуктов и куски прайса.
    Reranker (умной пересортировки) — нет. Все 10 чанков как есть идут в LLM. Порог 0.30 — низкий, в выдачу легко попадает шум.
  7. LLM формирует ответ. GPT-5 mini получает три блока:
    • system_prompt = prompts/askbiotact.txt + CRM-профиль клиента + критические ограничения (например "аллергия на молочное")
    • chat_history = последние сообщения из Redis (контекст диалога)
    • user message = шаблон "Данные из базы знаний: {10 чанков}\n\nСообщение клиента: {ОРИГИНАЛЬНЫЙ вопрос}"
    В LLM уходит оригинальный вопрос, не обогащённый. Обогащение работает только на этапе поиска (шаг 4 → 6).
  8. Отдаём ответ клиенту и сохраняем пару (вопрос + ответ) обратно в Redis.
  9. Параллельно (в фоне) — ExtractionAgent. gpt-4o-mini читает свежий обмен и сохраняет в Postgres структурированные инсайты: какие продукты упомянуты, симптомы, состав семьи, намерение, ограничения. Это пригодится в следующем запросе того же клиента (см. шаг 4а).

Bottlenecks и что можно сделать

От самого болезненного к косметике. Каждый пункт ссылается на конкретный шаг из слайда 2.

1. Обогащение вопроса — regex, а не LLM (шаг 4)

"А второй продукт сколько стоит?" — regex не поймёт, что речь о товаре из прошлого хода, если его нет в жёстком списке PRODUCT_NAMES. Insights из Postgres помогают, но они с прошлого хода — на первом коротком вопросе клиента их ещё нет.

добавить query-rewriting шаг — gpt-4o-mini переписывает вопрос с учётом 3-4 последних сообщений в самодостаточный поисковый запрос. Дешёво (~$0.0001/вопрос), сильно бьёт по качеству.

2. Один эмбеддинг — одна попытка поиска (шаги 5–6)

Если формулировка клиента "не попала" в формулировку карточки — выдача пустая или не та. Особенно болезненно для смешанных RU/UZ запросов.

multi-query (HyDE / 3 перефразировки → 3 поиска → объединить) или гибридный поиск (вектор + BM25 по тем же чанкам). Дороже один раз поднять, но качество растёт сильно.

3. Нет reranker'а, threshold 0.30 (шаг 6)

10 чанков как попало. Релевантный чанк может оказаться 8-м в списке — LLM хуже его читает (lost-in-the-middle). Шум на 0.30 тоже мешает.

cross-encoder reranker (Cohere Rerank / bge-reranker) на k=20 → топ-5 в LLM. Или поднять threshold до 0.45 и k=5.

4. В LLM уходит ОРИГИНАЛЬНЫЙ вопрос, не обогащённый (шаг 7)

Если поиск нашёл карточку BIFOLAK NEO благодаря склейке "BIFOLAK NEO а цена?", то LLM видит только "а цена?" — и сам должен догадаться по чанкам и истории. Иногда отвечает не про тот продукт.

передавать в LLM enriched_message или хотя бы явно вставлять "клиент спрашивал про X" в шаблон. Изменение в одну строку.

5. Один шанс на корректный ответ — нет evaluation loop

Если LLM ответил мимо, мы это узнаём только из жалоб клиента. Качество не измеряется автоматически.

собрать 30-50 эталонных вопросов с правильными ответами. Гонять их nightly после любого изменения промпта/чанков. Без этого каждое "улучшение" — наугад.

6. Цены живут отдельно от карточек (контент-проблема)

Чтобы ответить "сколько стоит BIFOLAK NEO", нужно найти ДВА чанка: карточку продукта и кусок prices.txt. Если вторая не попадёт в топ-10 — цены не будет в ответе.

либо положить цену прямо в карточку продукта (дублирование, но живучее), либо boost'ить prices.txt при price-query (сейчас просто добавляется текст-подсказка, но это не гарантия).

7. Async ExtractionAgent — race condition (шаг 9)

Инсайты пишутся в фоне. Если клиент шлёт следующий вопрос быстрее, чем завершился gpt-4o-mini — обогащение шага 4а не сработает (insight ещё пустой).

для активной сессии переключить на синхронный extraction (+~500ms задержки), либо хотя бы дожидаться его при is_short_query().

Что бы я сделал первым

Порядок по соотношению "усилие × эффект": (4) передавать enriched в LLM — 1 строка кода, мгновенно; (1) query rewriting — день работы, заметный скачок качества; (5) eval-сет — без него остальные изменения слепые. (3) reranker и (2) hybrid search — потом, когда eval покажет где боль.

Top 5 проектов — что взять в Navigator + Pilot

3 агента изучили 12 open-source проектов (читали реальный код, не маркетинг). Команда: Captain (ты) → Navigator (стратег между вопросом и поиском) → Pilot (chat LLM, формирует ответ).

1. Onyx — production-grade reference

github.com/onyx-dot-app/onyx · ~29k⭐ · MIT · Python/FastAPI + Vespa + LangGraph

Что круто: agent_search граф — expand → search → grade → rerank → verify → sub-answer → aggregate. Refined-answer loop если первый ответ слабый.

скелет LangGraph для Navigator + абстракция DocumentIndex — обернём Qdrant за интерфейсом, чтобы можно было A/B без переписывания pipeline.

2. LangGraph — скелет Navigator

github.com/langchain-ai/langgraph · ~31k⭐ · MIT · Python, StateGraph + Postgres checkpointer

Что круто: туториал agentic_rag — это буквально Navigator: generate_query_or_respond → retrieve → grade_documents → rewrite_question → generate_answer. Условные edges, typed state, persistence per user_id.

взять 4-нодовый скелет 1:1. Typed state: {messages, crm_card, extracted_slots, missing_slots, last_query}. Checkpoint в Postgres по telegram_id.

3. Letta / MemGPT — память для CRM-карточки

github.com/letta-ai/letta · ~22k⭐ · Apache-2.0 · Python + Postgres

Что круто: core memory blocks — структурированный JSON, который агент сам редактирует через tool-вызовы (core_memory_replace("symptoms", "...")). Инжектится в каждый промпт.

заменить async ExtractionAgent на синхронные core memory updates от Navigator. CRM-карточка перестаёт быть статичной "справкой" — становится живой структурой, которую Navigator пополняет каждый ход.

4. Quivr — заменить regex на 2 LLM-промпта

github.com/QuivrHQ/quivr · ~39k⭐ · Apache-2.0 · Python + LangGraph, YAML-описание pipeline

Что круто: CONDENSE_TASK_PROMPT (history-aware rewrite) + SPLIT_PROMPT (разбивает мульти-вопрос на отдельные). Pipeline объявлен в YAML — можно менять без правки кода.

самый дешёвый и быстрый апгрейд из всех. Убираем regex-склейку из constants.py:enrich_query, ставим 2 промпта gpt-4o-mini. Стоит ~$0.0002/запрос.

5. DSPy — Navigator, который сам себя оптимизирует

github.com/stanfordnlp/dspy · ~34k⭐ · MIT · Python, типизированные Signatures + оптимизаторы

Что круто: промпт пишется как контракт Signature("crm_card, history, user_msg → rewritten_query, missing_slots, clarify"), дальше MIPROv2 оптимизатор сам подбирает лучшие формулировки против метрики на эталонном сете.

Navigator = DSPy-программа. Когда соберём 50 эталонных диалогов RU/UZ — оптимизатор за ночь подберёт промпт лучше, чем мы вручную за неделю.

Honorable mentions (отдельные паттерны)

  • Khoj — единый prompts.py-реестр и Agent-as-DB-model. Для Pilot-промптов вместо разбросанных файлов.
  • R2R — 3-уровневый API (search/rag/agent). Дешёвые запросы могут идти мимо Navigator.
  • AnythingLLM — Workspace-абстракция. Мапится на текущий department_id=askbiotact.
  • MedRAG / i-MedRAG — follow_up_ask промпт для multi-query/HyDE расширения после Navigator.

Вердикт по Rust — остаёмся на Python

Bottleneck — I/O (OpenAI ~300-800ms + Qdrant ~20-50ms), оба сетевые. Rust ≈ Python для async I/O. Что Rust не даёт: ускорения там, где у нас боль.

Что теряем: скорость итерации промптов (это 80% работы над качеством), feature parity OpenAI SDK, hiring в Ташкенте, aiogram > teloxide для RU/UZ FSM.

Через 12 мес., если профайлер покажет CPU-bound hot path (custom reranker / chunker) — оборачиваем PyO3-модуль. Полный rewrite не оправдан. Изученные Rust-проекты worth knowing: rig, swiftide, fastembed-rs, LanceDB.

План: 4 фазы

  1. Фаза 1 (день): передать enriched_message в Pilot (1 строка, фикс bottleneck #4 со слайда 3) + один LLM-промпт CONDENSE от Quivr вместо regex. Уже видно улучшение.
  2. Фаза 2 (1-2 недели): Navigator = LangGraph граф (decide → retrieve → grade → answer) с typed state. Letta-style core memory для CRM-карточки. Логирование решений Navigator в Postgres.
  3. Фаза 3 (2 недели): Navigator переписан как DSPy Signature. Собираем 50 эталонных RU/UZ диалогов с правильными ответами. Запускаем MIPROv2 — он сам подбирает промпт. Здесь главный скачок качества.
  4. Фаза 4 (опционально): Cohere/BGE reranker (k=20 → top-5). Multi-query HyDE из MedRAG. Делаем только если eval показывает что retrieval — узкое место.
