## 1. Резюме

Предлагается переписать Biotact Platform с нуля, используя архитектуру **модульного монолита** вместо текущего неструктурированного монолита. Новая версия будет иметь чёткое разделение на слои, полное покрытие тестами и автоматизированный CI/CD pipeline.

---

## 2. Мотивация

### 2.1 Текущее состояние (v1)

Biotact Platform v1 — работающая RAG-система для фармацевтической компании. Однако текущая реализация имеет критические проблемы:

| Проблема | Влияние | Severity |
|----------|---------|----------|
| 0% test coverage | Невозможно безопасно рефакторить | Critical |
| Монолитный main.py (35KB) | Сложно поддерживать и расширять | High |
| Нет Alembic миграций | Ручное управление схемой БД | High |
| Ручной запуск сервисов | Downtime после перезагрузки сервера | Medium |
| Нет CI/CD | Ручной деплой, риск ошибок | High |
| Отсутствие type hints | Сложно понять контракты функций | Medium |

### 2.2 Бизнес-контекст

- **Пользователи:** 5 отделов компании (Marketing, Sales, Call Center, Logistics, Accounting)
- **Нагрузка:** ~100 запросов/день (низкая)
- **Рост:** Планируется добавление новых отделов и интеграций
- **Команда:** 1 разработчик

### 2.3 Цели v2

1. **Maintainability** — код легко понять и изменить
2. **Testability** — 70%+ unit test coverage
3. **Reliability** — автоматический деплой, мониторинг
4. **Extensibility** — легко добавлять новые модули (отделы)

## 3. Варианты решения

### 3.1 Вариант A: Микросервисы

```
┌─────────────┐  ┌─────────────┐  ┌─────────────┐
│ Auth Service│  │ Chat Service│  │ RAG Service │
└──────┬──────┘  └──────┬──────┘  └──────┬──────┘
       │                │                │
       └────────────────┼────────────────┘
                        │
                 ┌──────▼──────┐
                 │ API Gateway │
                 └─────────────┘
```

**Плюсы:**
- Независимое масштабирование сервисов
- Изоляция отказов
- Возможность использовать разные технологии

**Минусы:**
- Сложность: distributed transactions, service discovery
- Overhead: сетевые вызовы между сервисами (+10-50ms latency)
- Стоимость: нужен Kubernetes или аналог
- Overkill для команды из 1 человека и 100 req/day

**Вердикт:** ❌ Не подходит — избыточная сложность для текущего масштаба

### 3.2 Вариант B: Классический монолит

```
┌─────────────────────────────────┐
│           main.py               │
│  (всё в одном файле/папке)      │
└─────────────────────────────────┘
```

**Плюсы:**
- Простота деплоя
- Нет сетевого overhead
- Быстрая разработка на старте

**Минусы:**
- Сложно масштабировать команду
- Высокая связанность (coupling)
- Сложно тестировать изолированно
- То, что есть сейчас — и это проблема

**Вердикт:** ❌ Не подходит — это текущее состояние, которое нужно улучшить

### 3.3 Вариант C: Модульный монолит (Recommended)

```
┌─────────────────────────────────────────────────┐
│                  FastAPI App                     │
│  ┌───────────┐ ┌───────────┐ ┌───────────────┐  │
│  │   Core    │ │    API    │ │   Modules     │  │
│  │ ─────────-│ │ ─────────-│ │ ─────────────-│  │
│  │ config    │ │ /auth     │ │ marketing/    │  │
│  │ database  │ │ /chat     │ │ sales/        │  │
│  │ security  │ │ /health   │ │ call_center/  │  │
│  └───────────┘ └───────────┘ └───────────────┘  │
│  ┌───────────┐ ┌───────────┐ ┌───────────────┐  │
│  │ Services  │ │   Repos   │ │     RAG       │  │
│  │ ─────────-│ │ ─────────-│ │ ─────────────-│  │
│  │ auth      │ │ chat_repo │ │ embeddings    │  │
│  │ chat      │ │ user_repo │ │ retriever     │  │
│  │ rag       │ │           │ │ generator     │  │
│  └───────────┘ └───────────┘ └───────────────┘  │
└─────────────────────────────────────────────────┘
```

**Плюсы:**
- Чёткое разделение ответственности (Separation of Concerns)
- Легко тестировать каждый модуль изолированно
- Нет сетевого overhead
- Простой деплой (один процесс)
- Возможность выделить модуль в микросервис при необходимости
- Подходит для команды из 1-3 человек

**Минусы:**
- Нельзя масштабировать модули независимо
- Падение одного модуля = падение всего приложения
- Требует дисциплины в соблюдении границ модулей

**Вердикт:** ✅ **Рекомендуется** — оптимальный баланс простоты и структуры

## 4. Предлагаемое решение

### 4.1 Архитектура

Выбираем **модульный монолит** со следующими слоями:

```
┌─────────────────────────────────────────┐
│              API Layer                   │  ← HTTP endpoints (FastAPI routers)
├─────────────────────────────────────────┤
│            Service Layer                 │  ← Business logic
├─────────────────────────────────────────┤
│          Repository Layer                │  ← Data access (SQLAlchemy)
├─────────────────────────────────────────┤
│            Domain Models                 │  ← SQLAlchemy models, Pydantic schemas
├─────────────────────────────────────────┤
│           Infrastructure                 │  ← Database, Qdrant, external APIs
└─────────────────────────────────────────┘
```

**Правила зависимостей (Dependency Rule):**
- Верхние слои зависят от нижних
- Нижние слои НЕ знают о верхних
- API → Service → Repository → Models → Infrastructure

### 4.2 Структура проекта

```
biotact-core-v2/
├── src/biotact/
│   ├── main.py              # Entrypoint (минимальный!)
│   ├── core/                # Shared infrastructure
│   ├── models/              # SQLAlchemy models
│   ├── schemas/             # Pydantic schemas
│   ├── repositories/        # Data access
│   ├── services/            # Business logic
│   ├── api/v1/              # REST endpoints
│   ├── modules/             # Department modules
│   └── rag/                 # RAG engine
├── tests/
│   ├── unit/
│   └── integration/
└── docs/
```

### 4.3 Ключевые решения

| Решение | Выбор | Обоснование |
|---------|-------|-------------|
| Архитектура | Модульный монолит | Баланс простоты и структуры |
| Multi-tenancy | Payload-based в Qdrant | Одна коллекция, фильтр по department_id |
| ORM | SQLAlchemy 2.0 async | Современный async, type-safe |
| Validation | Pydantic v2 | Быстрая валидация, интеграция с FastAPI |
| Testing | pytest + pytest-asyncio | Стандарт для Python |
| CI/CD | GitHub Actions | Бесплатно, интеграция с GitHub |

## 5. Trade-offs и риски

### 5.1 Trade-offs

| Что получаем | Чем жертвуем |
|--------------|--------------|
| Простота деплоя | Нельзя масштабировать модули независимо |
| Нет сетевого latency | Общий failure domain |
| Лёгкое тестирование | Требует дисциплины в границах модулей |
| Быстрая разработка | Потенциальный рефакторинг при росте команды |

### 5.2 Риски и митигация

| Риск | Вероятность | Влияние | Митигация |
|------|-------------|---------|-----------|
| Нарушение границ модулей | Medium | High | Code review, архитектурные тесты |
| Рост сложности при масштабировании | Low | Medium | Готовность к выделению микросервисов |
| Падение всего приложения | Low | High | Health checks, graceful degradation |
